# Buddy AI — 模糊任务自动决策推进系统

## Auto-Decision Resolution System Spec

v0.1 Draft

-----

## 一、问题本质

会议纪要或日常对话中，AI 提取的任务经常存在信息缺失：负责人没定、截止日期不明、任务描述模糊、优先级未确认。

当前方案是给这些任务打上 ⚠️ 标签（needsReview=true），等相关人员自己发现并补全。但现实中没人会主动去翻”待补充信息”筛选器，这些模糊任务会永远烂在系统里，同时堵塞所有依赖它的下游工作。

**核心原则：被动信息永远没人看，只有主动推到人面前的信息才会被处理。**

-----

## 二、解决方案概述

每一个信息不完整的任务，系统自动裂变出一个”确认任务”（Decision Task），指派给最有可能做这个决策的人。确认任务有截止时间、有超时升级机制。相关人可以直接在 AI 对话中回复确认，系统自动更新原任务并清除 needsReview 标记。

### 整体流程

```
会议纪要输入
    ↓
AI 提取任务（现有能力）
    ↓
检测信息缺失（现有 warnings 机制）
    ↓
对每个有 warning 的任务 → 自动创建 Decision Task
    ↓
Decision Task 推送给决策人（AI 对话消息）
    ↓
决策人在对话中回复 → AI 解析回复 → 更新原任务 → 清除 needsReview → 标记 Decision Task 为 done
    ↓
超时未回复 → 24h 再次提醒 → 48h 升级通知给任务发起人
```

-----

## 三、Decision Task 数据模型

### 3.1 新增字段（tasks 表）

```
is_decision_task    boolean   default false    -- 是否是自动生成的确认任务
decision_for_task_id integer  FK→tasks         -- 关联的原始模糊任务 ID
decision_type       varchar(50)                -- 缺失的信息类型
decision_status     varchar(50) default 'pending'  -- pending | resolved | escalated
decision_deadline   timestamp                  -- 确认截止时间（创建后24h）
escalation_deadline timestamp                  -- 升级截止时间（创建后48h）
escalated_to_id     integer   FK→users         -- 升级通知给谁
```

### 3.2 decision_type 枚举值

|decision_type       |触发条件         |推送给谁            |
|--------------------|-------------|----------------|
|`assignee_unclear`  |负责人未明确或多人共担  |会议发起人 / 项目 owner|
|`deadline_missing`  |无截止日期或 AI 推测的|任务被暂分给的 assignee|
|`scope_unclear`     |任务描述模糊、缺少具体要求|任务被暂分给的 assignee|
|`priority_unclear`  |优先级不确定       |项目 owner        |
|`dependency_unclear`|前置依赖关系不明     |任务被暂分给的 assignee|

### 3.3 决策人选择逻辑

优先级从高到低：

1. 如果 warning 涉及”谁来做” → 推给**会议发起人**（即创建这批任务的用户）
1. 如果 warning 涉及”怎么做/什么时候” → 推给**被暂分配的 assignee**
1. 如果任务没有任何 assignee → 推给**项目 owner**
1. 如果以上都没有 → 推给**组织 admin**

## 四、AI 对话推送消息

### 4.1 初次推送（创建 Decision Task 时立即发送）

Decision Task 创建后，系统通过 AI 对话给决策人发一条结构化消息。不是普通文本，而是可交互的确认卡片。

**消息模板：**

```
📋 会议任务需要你确认

以下事项从 [会议名称/日期] 中提取，有些信息需要你补充：

1️⃣ 「有赞分销页面搭建」
   ⚠️ 负责人未确定，会议中说"后面再讨论"
   → 你觉得谁来负责？预计什么时候完成？

2️⃣ 「新客服试用期评估」
   ⚠️ Tina和安洲一起做，谁主导？
   → 请确认主负责人

3️⃣ 「竞品促销应对方案」
   ⚠️ 会上只口头提了一句，没有明确行动项
   → 需要立项吗？如果需要，谁来做、什么时候交？

直接回复即可，比如："1. 安洲做，下周五前；2. Tina主导；3. 先不立项"
```

**关键设计：**

- 每个待确认项有编号，决策人可以直接按编号回复
- 提供了回复示例，降低回复门槛
- 一条消息聚合该决策人的所有待确认项，不要一个一个发

### 4.2 AI 解析回复

决策人回复后，AI 需要：

1. 解析自然语言回复，匹配到对应的 Decision Task
1. 提取出确认的信息（负责人、截止日期、优先级等）
1. 更新原始任务的对应字段
1. 将原始任务的 needsReview 设为 false
1. 将 Decision Task 标记为 done
1. 回复确认：“✅ 已更新：「有赞分销页面搭建」→ 负责人：安洲，截止：下周五”

**如果回复仍然模糊：**
AI 追问一次，比如：“安洲做分销页面，截止日期你说’尽快’——能给个具体日期吗？”

### 4.3 超时提醒

**24 小时未回复 → 第一次提醒：**

```
⏰ 提醒：还有 3 个会议事项等你确认

「有赞分销页面搭建」「新客服试用期评估」「竞品促销应对」
这些任务的下游工作正在等待，请尽快回复。
```

**48 小时未回复 → 升级通知：**

将 decision_status 改为 `escalated`，给会议发起人（或组织 admin）发消息：

```
🔺 升级通知：[决策人姓名] 有 3 个待确认事项已超过 48 小时

原始会议：[日期] 的团队周会
未确认事项：「有赞分销页面搭建」「新客服试用期评估」「竞品促销应对」

这些任务的下游工作处于阻塞状态。你可以：
1. 直接帮他确认（回复具体信息）
2. 催他处理
```

## 五、与图谱的联动

### 5.1 Decision Task 在图谱上的表现

- Decision Task 作为一种特殊节点显示在图谱上
- 视觉标识：节点外圈有黄色虚线脉冲动画（区别于 blocked 的红色呼吸），表示”等待人类输入”
- 它跟原始任务之间有一条连线（type: `decision_dependency`），血管状态为淤积（因为 Decision Task 未完成 → 原始任务信息不全 → 下游堵塞）

### 5.2 级联可视化

当一个模糊任务有 3 个下游任务在等它时，图谱上的效果：

```
[Decision Task ⚠️] --淤积血管→ [模糊原任务 ⚠️] --淤积血管→ [下游任务A]
                                                --淤积血管→ [下游任务B]
                                                --淤积血管→ [下游任务C]
```

管理者在图谱上一眼就看到：这个黄色脉冲的节点堵住了一串东西，点进去发现是”有赞分销页面负责人没定”，问题的根源和影响范围同时清晰。

## 六、前端改动

### 6.1 AI 对话区

- 新增消息类型 `decision_request`，渲染为可交互的确认卡片（编号列表 + 每项的 warning + 回复输入提示）
- 决策人回复后，卡片上对应项自动标记为 ✅ 已确认，灰掉

### 6.2 任务详情页

- 如果任务有关联的 Decision Task（is_decision_task=true 且 decision_for_task_id 指向本任务），在任务详情页顶部显示黄色横幅：
  “⚠️ 此任务有信息待确认 — 已推送给 [决策人姓名]，等待回复中”
- 横幅上显示倒计时：距离超时提醒还有 X 小时

### 6.3 仪表盘

- “待补充”统计卡片改为”待确认决策”，数字 = 所有 pending 的 Decision Task 数量
- 点击进入列表，按超时紧急度排序

## 七、后端改动

### 7.1 Decision Task 自动创建

修改 AI 任务创建流程（用户确认 multi_confirm 后触发）：

```
对每个被确认创建的任务：
  如果 warnings 非空：
    对每个 warning：
      1. 确定 decision_type
      2. 确定决策人（按第三节的选择逻辑）
      3. 创建 Decision Task：
         - title: "确认：[原任务标题] — [缺失信息描述]"
         - assignee_id: 决策人
         - is_decision_task: true
         - decision_for_task_id: 原任务 ID
         - decision_type: 对应类型
         - decision_deadline: now + 24h
         - escalation_deadline: now + 48h
         - priority: 与原任务相同
      4. 给决策人发送 AI 对话消息（聚合该决策人的所有待确认项）
```

**优化：同一个决策人的多个 Decision Task 聚合为一条消息推送，不要逐条发。**

### 7.2 定时任务

新增两个 cron job（或用 setInterval 简化实现）：

- **每小时检查一次：** 扫描所有 decision_status=‘pending’ 的 Decision Task
  - 超过 decision_deadline 且未提醒过 → 发送提醒消息，记录已提醒
  - 超过 escalation_deadline → 改 decision_status=‘escalated’，给 escalated_to_id 发升级通知

### 7.3 AI 回复解析

在 AI Service 的 system prompt 中新增指令：

```
当用户回复的内容匹配到待确认的 Decision Task 时：
1. 提取确认信息
2. 输出 action type: "resolve_decision"
3. data 中包含：decision_task_id, 更新的字段和值
4. 系统收到后：更新原任务 → needsReview=false → Decision Task 标记 done
```

## 八、执行计划

**Phase 1（基础闭环）：**

- tasks 表加字段
- AI 创建任务时自动生成 Decision Task
- 给决策人发 AI 对话消息
- 决策人回复后 AI 解析并更新原任务

**Phase 2（超时机制）：**

- 24h 提醒 + 48h 升级
- 定时扫描任务

**Phase 3（图谱联动）：**

- Decision Task 节点在图谱上显示
- 黄色脉冲动画
- 跟原任务的连线和淤积血管效果

-----

## 九、设计原则

> **每一条模糊信息都是一个行动项，不是一个标签。**
> 标签是被动的，行动项是主动的。标签等人发现，行动项追着人跑。

> **系统的职责不是记录问题，而是推动问题被解决。**
> 如果一个任务信息不全，系统不应该只是标注”信息不全”然后等着。它应该立刻找到能补全信息的人，把问题推到他面前，给他截止时间，超时了就升级。

> **决策延迟是隐性的最大堵塞源。**
> 在图谱上，代码 bug 导致的 blocked 任务很容易被看到。但”负责人没定所以谁都没动”这种堵塞是隐形的——任务根本就没进入执行状态。Decision Task 系统把这种隐性堵塞显性化。
